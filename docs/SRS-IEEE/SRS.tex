\section{Introduction}

This document specifies Magic-8, a free-to-play, web-based 3D puzzle game built around an 8×8×8 magic cube.
It states the purpose, users, and project goals: to provide an engaging, navigable magic cube experience in which players complete tasks to practice addition and subtraction in base 8, supported by an introductory tutorial, guided hints, online competitive features, and task-based problem solving. 

The work is based on the provided IEEE SRS template provided in the course \citet{ISOIECIEEE29148_2018} with reference to the ISO/IEC/IEEE 29148:2018 template \citet{ISOIECIEEE29148_2018}, which justifies the SRS structure, 
and ISO/IEC/IEEE 15288:2023 \citet{ISOIECIEEE15288_2023}, which provides the broader life-cycle context underlying modern requirements engineering practice. Additional sections were added in the form of regulations and guiing protocols, and reasonable inputs \& outputs to increase the team's refinement of the project scope and definition.

\subsection{Purpose}

The project is intended to create a game involving an 8x8x8 magic cube that can be navigated by players through task completion to practice addition and subtraction in base 8.
The intent is to solve the lack of engaging resources available for learning and practicing mathematics in non-decimal number bases as alternative bases. Such as base 8, are rarely taught before post-secondary education.

The following sections will outline the scope, functional requirements and the non-functional requirements that the team will adhere to produce a game that is both educative and fun.

\subsection{Scope}
\label{subsec:scope}

\textbf{In-Scope and functionality}

The project known as Magic-8 will be a free-to-play web game where users will be presented with a 3D visualization of an 8$\times$8$\times$8 magic cube separated into slices.
Users receive a tutorial on addition and subtraction in base eight, a starting cell, and at least 8 tasks that, by solving the problems within, will navigate them through the cube as they move through its layers.
Users will gain points for correctly solving the problems in a task; these points will be tied to a user's personal account.

\textbf{Intended users}

Magic-8 primarily appeals to recreational math enjoyers who would enjoy a challenge while practicing a different base, and high school students and their teachers who gain a way to engagingly experience an unfamiliar base.
The goal is to create a system that can not only be used as a fun way to improve one's skill in addition and subtraction in bases but would also act as a ready-made introductory classroom tool for engaging students,
an experience that is helpful for aspiring STEM students due to how important base 8 and working with new number bases is in systems such as Unix, the C programming language, etc., with Magic-8 serving as an early introduction. As such,
the improved interest in numeracy stemming from a broader appreciation for alternative number bases benefits all those who would appreciate the greater interest, such as
post-secondary STEM professors, educational technology platforms, and society as a whole.

\textbf{Out of Scope}

The tool is aimed at being fun and educational; it is not intended to replace a curriculum or full octal tutorial; it is strictly web-based with no plans for mobile or offline development.
It supports octal only (no other bases, no 2D squares, no 4D tesseracts, no alternative rulesets, no automatic cube generation, no player puzzle generation, no decimal mode, although these may be considered as stretch goals after project completion).
Cubes of order other than 8 and 16 are excluded because they do not satisfy all 13 lines.

\textbf{Explicit assumptions}

The project assumes the following as true for the success of the project:
\begin{itemize}
\item A valid order 8 magic cube is available.
\item New valid cubes can be created be it algorithmically or through rotation of initial cube.
\item A user will not be able to memorize the positions of the 512 cells that make up the cube to bypass task interaction.
\item Users have browser capable devices and internet access.
\item Users posses basic numeracy.
\item The chosen implementation software's open source licenses are compatible with the distribution method.
\item Tasks are all solveable and their problems can be accurately conveyed to intended users.
\item Users are willing to engage with an octal system.
\end{itemize}

\subsection{Problem Statement}

%\plt{Current situation, problem, impact, desired improvement.  You will likely borrow some text from your problem description document.}

Magic cubes provide an opportunity to explore numerical patterns and mathematical 
relationships in 3-dimensions. However, understanding these structures can become
challenging due to limited sources as well as having to use static 2D images to understand
a 3D pattern.

The goal of this project is to create a recreational mathematics game that allows those interested
in these magic cubes as well as non standard number bases such as base 8 to further their understanding.
This is planned to be a web-based game in which users will be able to complete certain challenges on a 3d
representation of an 8x8x8 magic cube using base 8 mathematics to find patterns associated with a magic cube.
This will include adding values to certain sections of the cube to complete patterns of magic cubes moving through
8 stages of difficulty while continuing to learn about these mathematical structures.

\section{Functional Requirements}

\subsection{Formal Model}
\label{sec:formal-model}

This formal model describes the configuration of a game round, the
evaluation of tasks, and the calculation of the users score. It
defines the conditions under which a task is considered complete and
the properties that the scoring system must maintain. The model
supports the functional requirements concerning task execution,
answer evaluation, and score calculation (FR7--FR50).

\subsubsection{Game Configuration}

Let the set of tasks in a game round be
\[
    \mathcal{T} = \{T_1,T_2,\ldots,T_8\}.
\]

Each task \(T_i\) has an associated target condition and a basic
score value. 
Let:

\[
    B_i = B(T_i), \qquad B_i \in \mathbb{N}_0.
\]
Where \(B_i\) is the basic score awarded for correctly
completing task \(T_i\). The target conditions are defined by the
game configuration and are evaluated against the current puzzle
state.

The octal target values used by the game include
\[
    S_1 = 1001_8,\qquad
    S_2 = 2002_8,\qquad
    S_3 = 4004_8.
\]

These values are interpreted as octal numbers. For example,
\[
    1001_8 = 513_{10},\qquad
    2002_8 = 1026_{10},\qquad
    4004_8 = 2052_{10}.
\]

These values are used by the application to define their target conditions. For instance,
\[
    \theta_i(C) =
    \begin{cases}
        1, & \text{if } L_i(C) = s_i,\\
        0, & \text{otherwise}.
    \end{cases}
\]
where \(L_i(C)\) is the sum of relevant cells, and 
\[
    \theta_i(C) = 
    \begin{cases}
        1, & \text{if condition met}\\
        0, & \text{otherwise}.
    \end{cases}
\] 
is the target condition.

\subsubsection{Round State}

A game round is represented by the state
\[
    R = (C, i, A, P),
\]
where:
\begin{itemize}
    \item \textbf{Puzzle Configuration (\(C\)):}
    The current state of the magic cube, represented by a
    three-dimensional array of cell values:
    \[
        C \in V^{n \times n \times n},
    \]
    where \(n\) is the dimension of the cube and \(V\) is the
    set of permitted cell values, including any designated
    empty value used for unfilled cells. Each element
    \(C_{x,y,z}\) represents the value of the cell at position
    \((x,y,z)\), for \(1 \leq x,y,z \leq n\).

    \item \textbf{Current Task Index (\(i\)):}
    The index identifying the task currently being attempted:
    \[
        i \in \{1,2,\ldots,8\}.
    \]
    The value of \(i\) determines which task's completion
    conditions are evaluated against the current configuration
    \(C\).

    \item \textbf{Attempt Set (\(A\)):}
    The set of task attempts recorded during the round:
    \[
        A \subseteq
        \{(j,C_j,t_j,q_j) \mid
        j \in \{1,\ldots,8\}\},
    \]
    where \(j\) identifies the task, \(C_j\) is the cube
    configuration submitted for evaluation, \(t_j\) is the
    elapsed time associated with the attempt, and
    \(q_j \in \{0,1\}\) indicates whether the attempt was
    unsuccessful (\(0\)) or successful (\(1\)).
    Each recorded attempt therefore contains sufficient
    information to identify the task, the evaluated
    configuration, its elapsed time, and its result.

    \item \textbf{Accumulated Score (\(P\)):}
    The total score awarded to the player during the round:
    \[
        P \in \mathbb{N}_0,
        \qquad
        P = \sum_{j=1}^{8} W_j,
    \]
    where \(W_j\) is the score awarded for task \(T_j\), and
    \(\mathbb{N}_0\) denotes the non-negative integers.
    A task contributes to \(P\) only when it has been completed
    successfully and its score has not already been awarded.
\end{itemize}

The round state must remain consistent after every accepted
state transition. In particular, the accumulated score \(P\)
must agree with the recorded task rewards, and unsuccessful
attempts must not increase the score.

The current task index satisfies
\[
    1 \leq i \leq 8.
\]

For each task \(T_i\), let \(E_i(C)\) be the evaluation function
that returns true when the puzzle configuration \(C\) satisfies
the task's required conditions and false otherwise:
\[
    E_i(C) =
    \begin{cases}
        1, & \text{if task } T_i \text{ is satisfied},\\
        0, & \text{otherwise}.
    \end{cases}
\]

An attempt is considered successful only when the corresponding
evaluation function returns \(1\). Changes to the puzzle state
must be evaluated against the requirements of the current task.

\subsubsection{Task Evaluation}

Let \(a_i\) represent an attempt to complete task \(T_i\). The
result of evaluating the attempt is
\[
    \operatorname{Result}(a_i) = E_i(C).
\]

A successful attempt satisfies the task's target condition.
An unsuccessful attempt does not satisfy that condition and must
not be treated as a completed task.

The task completion indicator is defined as
\[
    Q_i =
    \begin{cases}
        1, & \text{if task } T_i \text{ has been completed correctly},\\
        0, & \text{otherwise}.
    \end{cases}
\]
This acts as a persistent tracker of completion even after the next task begins changing \(E_i(C)\).

For a round containing eight tasks, the number of completed tasks is
\[
    N_{\mathrm{completed}}
    = \sum_{i=1}^{8} Q_i.
\]

Consequently,
\[
    0 \leq N_{\mathrm{completed}} \leq 8.
\]

A task can contribute to the completed-task count only after its
correct completion has been established by the evaluation function.

\subsubsection{Timed Scoring}

Let \(B_i\) be the basic score for task \(T_i\), and let \(t_i\)
be the elapsed time, in seconds, associated with its successful
completion. For \(t_i > 0\), the timed score is calculated as
\[
    \operatorname{TimedScore}_i
    =
    \operatorname{round}
    \left(
        \frac{B_i \cdot 1350}{t_i}
    \right).
\]

Here, \(\operatorname{round}\) denotes rounding to the nearest
integer. The scoring rule rewards correct completion while taking
the time required to complete the task into account.

The score awarded for task \(T_i\) is defined as
\[
    W_i =
    \begin{cases}
        \operatorname{TimedScore}_i,
        & \text{if } Q_i = 1 \text{ and the score has not been awarded},\\
        0, & \text{otherwise}.
    \end{cases}
\]

The total score for a round is therefore
\[
    P = \sum_{i=1}^{8} W_i.
\]

This definition ensures that the total score is the sum of the
individual task scores and that an unsuccessful attempt does not
contribute points. A completed task must not be awarded points
more than once within the same round.

\subsubsection{Formal Properties}

The following properties describe expected behaviour of the task
evaluation and scoring system.

\paragraph{Theorem 1: Correctness of Task Completion.}

For any task \(T_i\), the task is considered successfully completed
only if its evaluation function returns true:
\[
    Q_i = 1 \implies E_i(C) = 1.
\]

\textit{Justification.}
By definition, task completion depends on satisfying the task's
required conditions. An attempt that fails evaluation cannot be
recorded as a successful completion.

\paragraph{Theorem 2: No Score for an Unsuccessful Attempt.}

For any task \(T_i\),
\[
    Q_i = 0 \implies W_i = 0.
\]

\subsection{Scope}

\begin{itemize}
\item \textbf{Order 8 cube (Section\ref{subsec:scope}):} An order 8 cube is chosen as it is the smallest most perfect magic cube.
\item \textbf{Fixed cube and no player generation (Section\ref{subsec:scope}):} The cube being used is fixed, with players being unable to generate their own, as a single cube can generate a large number of puzzles and
would massively balloon the scope and difficulty in assuring all cubes are perfect magic cubes.
\item \textbf{Browser based play (Section\ref{subsec:scope}):} The game is strictly web-based as we believe a browser-based game is sufficient to reach a large enough number of our intended users; browser play maximizes access across devices
and locations.
\end{itemize}

\subsection{Nonfunctional Requirements}

\begin{itemize}

\item \textbf{Performance
(NFR\ref{NFR_1},
NFR\ref{NFR_2}):}

Cube manipulation and cell-value editing are two of the most frequent
interactions in the magic cube game. These operations need to provide
prompt feedback so that users can understand the effects of their
actions without unnecessary delays.

\item \textbf{Usability
(NFR\ref{NFR_3},
NFR\ref{NFR_4},
NFR\ref{NFR_5},
NFR\ref{NFR_6}):}

The usability requirements focus on the primary tasks that users
must perform to interact with the puzzle successfully. These tasks 
represent the essential interaction workflow.
Requiring at least 80\% of usability evaluation participants to
complete these tasks without external assistance provides a
measurable baseline for whether the interface is
understandable to its intended users or not.

\item \textbf{Maintainability
(NFR\ref{NFR_7},
NFR\ref{NFR_8}):}

Separating mathematical operations, user-interface behaviour,
3D visualization, and online storage into identifiable
components reduces coupling between unrelated responsibilities.
This decision allows individual components to be modified with less
risk of affecting other parts of the system.

\item \textbf{Portability
(NFR\ref{NFR_9},
NFR\ref{NFR_10}):}

The system is intended to be accessed through desktop and laptop
web browsers rather than a platform-specific desktop application.
Browser-based deployment reduces installation requirements and
allows users to access the game through supported environments
without installing Python or additional standalone software.

\item \textbf{Reliability
(NFR\ref{NFR_11},
NFR\ref{NFR_12},
NFR\ref{NFR_13}):}

The correctness of the puzzle state is essential because subsequent
calculations, visual updates, and user interactions depend on it.
Separately defining requirements for valid state maintenance,
invalid input handling, and online failure handling ensures that
the system can respond predictably to both expected operations
and error conditions.

\item \textbf{Security and Privacy
(NFR\ref{NFR_14},
NFR\ref{NFR_15},
NFR\ref{NFR_16},
NFR\ref{NFR_17}):}

Because the system may support user accounts and online storage,
appropriate measures are needed to protect user information.
Encrypted network communication protects data during transmission,
while access restrictions prevent users from accessing other
accounts' private data.

\item \textbf{Accessibility
(NFR\ref{NFR_18},
NFR\ref{NFR_19}):}

The system should provide alternative ways for users to interact
with and understand the puzzle. Keyboard-operable controls support
users who cannot rely on pointer-based interaction, while sufficient
visual contrast helps make interface elements distinguishable.

\end{itemize}

\subsection{Appendix B: Development Plan}

This section describes the phased implementation for the functional requirements listed in the document; it is
organized around hedging the major risks of 3D visualization and the base game's core gameplay sequence.

\subsubsection{Phase 1: Proof of concept}

 Phase 1 is the POC, a hardcoded, minimal version of the game aimed at validating the two main risks. 
 The requirements involved in this part are: 
  \begin{itemize}
  \item Round setup: FR1, FR2, FR3, FR4, FR5 
  \item cell interaction: FR7, FR8, FR9, FR10, FR11, FR12, FR13, FR14, FR15, FR16, FR17, F18
  \item 3D Visualization: FR32, FR33, FR34, FR35. FR36 is excluded as it is an extension of FR36 aimed at improving accessibility.
  \item Task implementation: FR19, FR20, FR21, FR22; these are all checks that should be available even in a hardcoded version of tasks.
  \end{itemize}

  \textbf{Success criteria:} The cube fully renders and can be navigated according to the 3D visualization requirements; the user must be able to complete
  all 8 tasks without logic issues. If the 3D visualization fails, a transition to a different implementation method or 2D must be evaluated.

\subsubsection{Phase 2: Core game loop implementation}

This phase is aimed around randomization of the round setup and completing the scoring and task evaluation system.
The requirements involved in this part are: 
\begin{itemize}
\item Round setup: FR1, FR2, FR3, FR4, FR5 must still hold and FR6 is added to ensure randomization constantly changes the starting voxel.
\item Task Execution: FR19, FR20, FR21, FR22 must all still hold and FR23 and FR24 will be used to verify the task works with a randomized starting voxel.
\item Integrity check: FR25 to verify expected answers and verify the validity of task lines.
\item Scoring: FR26, FR27, FR28 which will revolve around verifying the points scoring, time-based scoring, and score display.
\item Stop and reset: FR29 to ensure the game loop can be stopped.
\end{itemize}
 
\textbf{Success criteria:} A full round of 8 randomized tasks must be playable from start to finish.
The system must correctly accept valid answers and update the user's score while rejecting invalid or incorrect ones. The
integrity checks must pass on every generated task, scores must be computed and displayed on every round, and the STOP GAME button must end the round and erase that round's progress.

\subsubsection{Phase 3: Improved 3D visualization and Navigation}

This phase is aimed at upgrading the 3D visualization implemented in the game, improving usability and accessibility.
The requirements involved in this part are: 
\begin{itemize}
\item View Switching: FR23
\item Navigation: FR33
\item Layer control: FR34
\item Highlighting: FR35
\item Accessibility: FR36
\end{itemize}

\textbf{Success criteria:} Users must be able to switch between slice and 3D views at any time without progressing the round state or pausing the timer; rotation and zoom must work with
both pointer and keyboard input. Any layer along the axis must be selectable, interactable, and restorable, with chosen layers being highlighted.
The four defined appearances must be distinguishable via means other than just color, and at least 80\% of users in the usability test must be able to perform rotation and layer selection without assistance.

\subsubsection{Phase 4: Learning phase}

This phase focuses on adding the educational aspect and guided learning through the tutorial and explanation features.
The requirements involved in this part are: 
\begin{itemize}
\item Interactive tutorial: FR37
\item Mistake explanation: FR38
\item Worked calculations: FR39
\item Hints: FR40 and FR41
\end{itemize}

\textbf{Success criteria:} A first-time user must be able to complete the interactive tutorial on their own and practice all eight tasks. The skip, exit, and replay features must be functioning.
The hint system should display a message naming the task/line type and its rules without revealing the correct cell, and the worked calculations should be available on request after answering incorrectly.

\subsubsection{Phase 5: Online feature phase}

The goal of this phase is to implement all the features with the creation of user account creation/deletion, leaderboards, round records, and daily challenges.
The requirements involved in this part are: 
\begin{itemize}
\item Guest Play: FR42.
\item Account Management: FR43, FR44, FR45, FR46.
\item Statistics: FR47, FR48.
\item Leaderboards: FR49, FR50.
\item Daily challenge: FR51, FR52.
\item Account deletion: FR53.
\end{itemize}

\textbf{Success criteria:} Users must be able to play without an account with none of their data being stored. Account creation must enforce unique usernames and emails that meet the prohibited term rules,
a password that meets the safety definition; invalid inputs must be rejected with a reason, with the reset feature working without revealing which credential was wrong.
Completed rounds must record the user's final score, scoring base, total time, and date; statistics must be displayed and leaderboards must show at least the top 10 scores and times with the username.
Leaderboards and statistic records must be created only from complete rounds and reject any other requests; the daily challenge must present the same challenge to every user with an accompanying summary.
Account deletion must remove all user data, verified by post-deletion queries.
 
\subsubsection{Phase 6: Recovery phase}

This phase is focused on increasing the system's resilience and interruption handling capability.
The requirements involved in this part are: 
\begin{itemize}
\item Auto-save: FR30
\item Round restoration: FR31
\end{itemize}

\textbf{Success criteria:} Any round in progress must be saved automatically on each state change, with the system trying at least 3 times upon save failure and notifying the user if all attempts fail.
After a page closes, reloads, or crashes, the system must check the saved round's validity and offer the user the option of resuming the timer at its saved value while discarding improper saves and informing the user.
Automated tests should simulate the state save failures and invalid saved states to confirm retry behavior, user notification, and safe discard.

This phase is deferrable if timeline limitations apply as the game is fully playable without it.

\subsubsection{Phase 7: Stretch goal implementations}

After the completion of the initial system, the team will be free to explore out-of-scope stretch goals such as the following:
\begin{itemize}
\item Creation of cubes in other number bases.
\item Alternative rulesets and objectives such as partial square completion rounds.
\item Automatic generation of new magic cube formations.
\item Player puzzle generation.
\item Offline play. 
\end{itemize}

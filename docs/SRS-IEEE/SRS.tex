\subsection{Problem Statement}

%\plt{Current situation, problem, impact, desired improvement.  You will likely borrow some text from your problem description document.}

Magic cubes provide an opportunity to explore numerical patterns and mathematical 
relationships in 3-dimensions. However, understanding these structures can become
challenging due to limited sources as well as having to use static 2D images to understand
a 3D pattern.

The goal of this project is to create a recreational mathematics game that allows those interested
in these magic cubes as well as non standard number bases such as base 8 to further their understanding.
This is planned to be a web-based game in which users will be able to complete certain challenges on a 3d
representation of an 8x8 magic cube using base 8 mathematics to find patterns associated with a magic cube.
This will include adding values to certain sections of the cube to complete patterns of magic cubes moving through
8 stages of difficulty while continuing to learn about these mathematical structures.

\section{Functional Requirements}

\subsection{Formal Model}
\label{sec:formal-model}

This formal model describes the configuration of a game round, the
evaluation of tasks, and the calculation of the users score. It
defines the conditions under which a task is considered complete and
the properties that the scoring system must maintain. The model
supports the functional requirements concerning task execution,
answer evaluation, and score calculation (FR7--FR50).

\subsubsection{Game Configuration}

Let the set of tasks in a game round be
\[
    \mathcal{T} = \{T_1,T_2,\ldots,T_8\}.
\]

Each task \(T_i\) has an associated target condition and a basic
score value. 
Let:

\[
    B_i = B(T_i), \qquad B_i \in \mathbb{N}_0.
\]
Where \(B_i\) is the basic score awarded for correctly
completing task \(T_i\). The target conditions are defined by the
game configuration and are evaluated against the current puzzle
state.

The octal target values used by the game include
\[
    S_1 = 1001_8,\qquad
    S_2 = 2002_8,\qquad
    S_3 = 4004_8.
\]

These values are interpreted as octal numbers. For example,
\[
    1001_8 = 513_{10},\qquad
    2002_8 = 1026_{10},\qquad
    4004_8 = 2052_{10}.
\]

These values are used by the application to define their target conditions. For instance,
\[
    \theta_i(C) =
    \begin{cases}
        1, & \text{if } L_i(C) = s_i,\\
        0, & \text{otherwise}.
    \end{cases}
\]
where \(L_i(C)\) is the sum of relevant cells, and 
\[
    \theta_i(C) = 
    \begin{cases}
        1, & \text{if condition met}\\
        0, & \text{otherwise}.
    \end{cases}
\] 
is the target condition.

\subsubsection{Round State}

A game round is represented by the state
\[
    R = (C, i, A, P),
\]
where:
\begin{itemize}
    \item \textbf{Puzzle Configuration (\(C\)):}
    The current state of the magic cube, represented by a
    three-dimensional array of cell values:
    \[
        C \in V^{n \times n \times n},
    \]
    where \(n\) is the dimension of the cube and \(V\) is the
    set of permitted cell values, including any designated
    empty value used for unfilled cells. Each element
    \(C_{x,y,z}\) represents the value of the cell at position
    \((x,y,z)\), for \(1 \leq x,y,z \leq n\).

    \item \textbf{Current Task Index (\(i\)):}
    The index identifying the task currently being attempted:
    \[
        i \in \{1,2,\ldots,8\}.
    \]
    The value of \(i\) determines which task's completion
    conditions are evaluated against the current configuration
    \(C\).

    \item \textbf{Attempt Set (\(A\)):}
    The set of task attempts recorded during the round:
    \[
        A \subseteq
        \{(j,C_j,t_j,q_j) \mid
        j \in \{1,\ldots,8\}\},
    \]
    where \(j\) identifies the task, \(C_j\) is the cube
    configuration submitted for evaluation, \(t_j\) is the
    elapsed time associated with the attempt, and
    \(q_j \in \{0,1\}\) indicates whether the attempt was
    unsuccessful (\(0\)) or successful (\(1\)).
    Each recorded attempt therefore contains sufficient
    information to identify the task, the evaluated
    configuration, its elapsed time, and its result.

    \item \textbf{Accumulated Score (\(P\)):}
    The total score awarded to the player during the round:
    \[
        P \in \mathbb{N}_0,
        \qquad
        P = \sum_{j=1}^{8} W_j,
    \]
    where \(W_j\) is the score awarded for task \(T_j\), and
    \(\mathbb{N}_0\) denotes the non-negative integers.
    A task contributes to \(P\) only when it has been completed
    successfully and its score has not already been awarded.
\end{itemize}

The round state must remain consistent after every accepted
state transition. In particular, the accumulated score \(P\)
must agree with the recorded task rewards, and unsuccessful
attempts must not increase the score.

The current task index satisfies
\[
    1 \leq i \leq 8.
\]

For each task \(T_i\), let \(E_i(C)\) be the evaluation function
that returns true when the puzzle configuration \(C\) satisfies
the task's required conditions and false otherwise:
\[
    E_i(C) =
    \begin{cases}
        1, & \text{if task } T_i \text{ is satisfied},\\
        0, & \text{otherwise}.
    \end{cases}
\]

An attempt is considered successful only when the corresponding
evaluation function returns \(1\). Changes to the puzzle state
must be evaluated against the requirements of the current task.

\subsubsection{Task Evaluation}

Let \(a_i\) represent an attempt to complete task \(T_i\). The
result of evaluating the attempt is
\[
    \operatorname{Result}(a_i) = E_i(C).
\]

A successful attempt satisfies the task's target condition.
An unsuccessful attempt does not satisfy that condition and must
not be treated as a completed task.

The task completion indicator is defined as
\[
    Q_i =
    \begin{cases}
        1, & \text{if task } T_i \text{ has been completed correctly},\\
        0, & \text{otherwise}.
    \end{cases}
\]
This acts as a persistent tracker of completion even after the next task begins changing \(E_i(C)\).

For a round containing eight tasks, the number of completed tasks is
\[
    N_{\mathrm{completed}}
    = \sum_{i=1}^{8} Q_i.
\]

Consequently,
\[
    0 \leq N_{\mathrm{completed}} \leq 8.
\]

A task can contribute to the completed-task count only after its
correct completion has been established by the evaluation function.

\subsubsection{Timed Scoring}

Let \(B_i\) be the basic score for task \(T_i\), and let \(t_i\)
be the elapsed time, in seconds, associated with its successful
completion. For \(t_i > 0\), the timed score is calculated as
\[
    \operatorname{TimedScore}_i
    =
    \operatorname{round}
    \left(
        \frac{B_i \cdot 1350}{t_i}
    \right).
\]

Here, \(\operatorname{round}\) denotes rounding to the nearest
integer. The scoring rule rewards correct completion while taking
the time required to complete the task into account.

The score awarded for task \(T_i\) is defined as
\[
    W_i =
    \begin{cases}
        \operatorname{TimedScore}_i,
        & \text{if } Q_i = 1 \text{ and the score has not been awarded},\\
        0, & \text{otherwise}.
    \end{cases}
\]

The total score for a round is therefore
\[
    P = \sum_{i=1}^{8} W_i.
\]

This definition ensures that the total score is the sum of the
individual task scores and that an unsuccessful attempt does not
contribute points. A completed task must not be awarded points
more than once within the same round.

\subsubsection{Formal Properties}

The following properties describe expected behaviour of the task
evaluation and scoring system.

\paragraph{Theorem 1: Correctness of Task Completion.}

For any task \(T_i\), the task is considered successfully completed
only if its evaluation function returns true:
\[
    Q_i = 1 \implies E_i(C) = 1.
\]

\textit{Justification.}
By definition, task completion depends on satisfying the task's
required conditions. An attempt that fails evaluation cannot be
recorded as a successful completion.

\paragraph{Theorem 2: No Score for an Unsuccessful Attempt.}

For any task \(T_i\),
\[
    Q_i = 0 \implies W_i = 0.
\]

\begin{itemize}

\item \textbf{Performance
(NFR\ref{NFR_1},
NFR\ref{NFR_2}):}

Cube manipulation and cell-value editing are two of the most frequent
interactions in the magic cube game. These operations need to provide
prompt feedback so that users can understand the effects of their
actions without unnecessary delays.

\item \textbf{Usability
(NFR\ref{NFR_3},
NFR\ref{NFR_4},
NFR\ref{NFR_5},
NFR\ref{NFR_6}):}

The usability requirements focus on the primary tasks that users
must perform to interact with the puzzle successfully. These tasks 
represent the essential interaction workflow.
Requiring at least 80\% of usability evaluation participants to
complete these tasks without external assistance provides a
measurable baseline for whether the interface is
understandable to its intended users or not.

\item \textbf{Maintainability
(NFR\ref{NFR_7},
NFR\ref{NFR_8}):}

Separating mathematical operations, user-interface behaviour,
3D visualization, and online storage into identifiable
components reduces coupling between unrelated responsibilities.
This decision allows individual components to be modified with less
risk of affecting other parts of the system.

\item \textbf{Portability
(NFR\ref{NFR_9},
NFR\ref{NFR_10}):}

The system is intended to be accessed through desktop and laptop
web browsers rather than a platform-specific desktop application.
Browser-based deployment reduces installation requirements and
allows users to access the game through supported environments
without installing Python or additional standalone software.

\item \textbf{Reliability
(NFR\ref{NFR_11},
NFR\ref{NFR_12},
NFR\ref{NFR_13}):}

The correctness of the puzzle state is essential because subsequent
calculations, visual updates, and user interactions depend on it.
Separately defining requirements for valid state maintenance,
invalid input handling, and online failure handling ensures that
the system can respond predictably to both expected operations
and error conditions.

\item \textbf{Security and Privacy
(NFR\ref{NFR_14},
NFR\ref{NFR_15},
NFR\ref{NFR_16},
NFR\ref{NFR_17}):}

Because the system may support user accounts and online storage,
appropriate measures are needed to protect user information.
Encrypted network communication protects data during transmission,
while access restrictions prevent users from accessing other
accounts' private data.

\item \textbf{Accessibility
(NFR\ref{NFR_18},
NFR\ref{NFR_19}):}

The system should provide alternative ways for users to interact
with and understand the puzzle. Keyboard-operable controls support
users who cannot rely on pointer-based interaction, while sufficient
visual contrast helps make interface elements distinguishable.

\end{itemize}

\section{Introduction}

\subsection{Background}

A most perfect magic cube is a cube where each voxel's value is a distinct number from 1 to n\textasciicircum{}3 and all rows, columns, pillars, 2-dimensional diagonals, 3-dimensional diagonals (triagonals), and broken space diagonals in the cube sum to the same number, also called the magic constant. The order-eight cube is the smallest order most perfect magic cube. Using octal within this order-8 magic cube showcases the magic properties of the cube with the above prescribed lines summing to 4004, half lines summing to 2002, and the complementary numbers (+4 4 4 for the x y z coordinates from a given voxel) summing to 1001 (all in octal).

Our project, Magic 8, is a web-based application that serves as a recreational mathematics game as well as an educational tool for octal addition and subtraction. In this proposed game, players start with one voxel (number) in a most perfect magic cube visible while all other voxels remain hidden. The player must then complete tasks related to finding the voxels belonging to lines that sum to the magic constant. Each round of the game includes eight tasks that increase in difficulty as the player progresses.

\subsection{Hazard Definition}

A hazard is defined as a system state that if combined with a specific environmental condition, can cause harm/damage. Hazards can result from software defects or incorrectly defined system behavior. These hazards can be categorized as health, data, education, and usability hazards.

\section{Scope and Purpose of Hazard Analysis}\label{sec:ScopeandPurpose}

The purpose of this Hazard Analysis is to identify hazards related to the Magic 8 application and subsequently perform a Failure Mode and Effect Analysis (FMEA) to mitigate the found hazards. Below is the description of the losses that could be incurred because of the hazards. Out of scope features include accessibility concerns, advanced cybersecurity (beyond simply encrypting data and securing passwords), and optimizing or extending the software for outdated or insufficient user hardware or software. Although these considerations will be important for future updates (past the capstone timeline), they do not fit within the scope of a first official version of the application.

\subsection{Health}

This category is described as the loss of health due to use of the system. This includes both physical health (e.g., photosensitive seizure, see \cite{PhotoSeizure}) as well as mental health (e.g., bullying through the application and addiction).

\subsection{Data}

This category is described as the deletion, corruption, or leakage of data. One loss related to this category is the unauthorized disclosure of private user account information (e.g., password). Another loss is the corruption or deletion of data (both user data as well as game data).

\subsection{Education}

This category is described as the loss of educational value. This involves harming the user's knowledge of octal addition and subtraction by either teaching them incorrectly or adding to their confusion of the mathematical concept.

\subsection{Usability}

This category is described as the loss of user engagement, satisfaction, or trust. Any of these losses would reduce the usability of the application and subsequently make it a less valuable product.

\section{Critical Assumptions}

The following are critical assumptions that are made about the system. These are necessary so that the scope of the analysis can be focused on realistic and manageable hazards.

One assumption is that users operate modern, standards-compliant web browsers. Another assumption is that external hosting providers meet uptime targets. A third assumption is that the external services the system uses for data storage have general protections against malicious behaviour, reducing but not removing data risks. Finally, it is assumed that external libraries are free from critical vulnerabilities (however manual checks will still be done to insure the content is reasonable).

\section{Safety and Security Requirements}

This section outlines the Safety and Security Requirements that were developed from the FMEA table.\newline

\noindent\textbf{SR1\label{req:SR1}:} The system shall encrypt sensitive user data.

\noindent\textbf{SR2\label{req:SR2}:} The system shall store user account passwords as cryptographic hashes.

\noindent\textbf{SR3\label{req:SR3}:} The system shall automatically generate a backup for each database.

\noindent\textbf{SR4\label{req:SR4}:} The system shall log all transactions for each database.

\noindent\textbf{SR5\label{req:SR5}:} The system shall automatically save game progress every time there is a change in game state.

\noindent\textbf{SR6\label{req:SR6}:} The system shall attempt to save the game state three times before failing and notifying the user.

\noindent\textbf{SR7\label{req:SR7}:} The system shall ensure that a save state is valid before loading it as the current game state.

\noindent\textbf{SR8\label{req:SR8}:} The system shall ensure that each generated task has not already been generated in the current round.

\noindent\textbf{SR9\label{req:SR9}:} The system shall ensure that each generated task is solvable.

\noindent\textbf{SR10\label{req:SR10}:} The system shall only allow authorized users to modify competitive statistics and leaderboard records.

\noindent\textbf{SR11\label{req:SR11}:} The system shall restore database data from the most recent, valid backup in the event of database corruption or data loss.

\noindent\textbf{SR12\label{req:SR12}:} The system shall ensure that a generated solution correctly solves its related generated task.

\noindent\textbf{SR13\label{req:SR13}:} The system shall ensure that public usernames meet guidelines for user conduct.

\noindent\textbf{SR14\label{req:SR14}:} The system shall warn the user if their hardware specification does not meet minimum requirements to run the application.

\noindent\textbf{SR15\label{req:SR15}:} The system shall ensure that the rendered cube and highlighting is consistent with the current game state.

\noindent\textbf{SR16\label{req:SR16}:} The system shall allow users to confirm parsed data before submitting.

\noindent\textbf{SR17\label{req:SR17}:} The system shall inform the user if an input event is not recognized.

\noindent\textbf{SR18\label{req:SR18}:} The system shall ensure that the displayed competitive/leaderboard is up to date (synchronized with the Competitive / Leaderboard Database).

\noindent\textbf{SR19\label{req:SR19}:} The system shall allow users to disable animations that may induce photosensitive seizures.

\noindent\textbf{SR20\label{req:SR20}:} The system shall ensure that the Tutorial / Hint Manager is synchronized with the current game state.

\noindent\textbf{SR21\label{req:SR21}:} The system shall remind the user how long they have been playing every hour.

\section{Roadmap}

This section outlines which safety and security requirements will be implemented as part of the capstone timeline, and which safety and security requirements will be deferred. The requirements implemented as part of the capstone timeline are considered high priority requirements.

\subsection{Safety and Security Requirements for Capstone Timeline}

\begin{itemize}
    \item \hyperref[req:SR1]{SR1}: It is important that our user data is secure as we are planning to release the game on the internet within the capstone timeline.
    \item \hyperref[req:SR2]{SR2}: Similar to \hyperref[req:SR1]{SR1}, it is important that the user accounts are secure as we are planning to release the game on the internet within the capstone timeline.
    \item \hyperref[req:SR5]{SR5}: An important game mechanic is saving the game state to ensure that the application is convenient for users.
    \item \hyperref[req:SR6]{SR6}: Similar to \hyperref[req:SR5]{SR5}, saving the game state is an important mechanic and ensures that the application allows users to exit and resume play.
    \item \hyperref[req:SR7]{SR7}: Ensuring that a save state is valid before loading is crucial to ensure that the game does not crash the game if the save is corrupted.
    \item \hyperref[req:SR8]{SR8}: An important goal in our game is user engagement. If a generated task is duplicated, user satisfaction could be significantly decreased.
    \item \hyperref[req:SR9]{SR9}: If a task is not solvable, user frustration and confusion will increase. This increases the chance that users will abandon the game.
    \item \hyperref[req:SR12]{SR12}: If a solution does not correctly solve the current task, user frustration and confusion will increase. This increases the chance that users will abandon the game.
    \item \hyperref[req:SR13]{SR13}: Because we are planning to release the game on the internet within the capstone timeline, it is important that we protect our users from harmful language.
    \item \hyperref[req:SR14]{SR14}: Notifying the user if their hardware specifications do not meet minimum requirements is important because it gives the user an actionable fix if they are experiencing performance issues with the game.
    \item \hyperref[req:SR15]{SR15}: Incorrect highlighting can increase user frustration and confusion, leading to decreased user engagement, satisfaction, and education.
    \item \hyperref[req:SR16]{SR16}: By allowing users to confirm parsed data before submitting, the chance of the user submitting parsed information that they did not intend decreases. In turn, this improves user satisfaction.
    \item \hyperref[req:SR17]{SR17}: By informing users when input events are not recognized, users can better understand what is going wrong. This will reduce user confusion.
    \item \hyperref[req:SR18]{SR18}: One of the main features for the capstone timeline is competitive statistics and leaderboards. Therefore, it is imperitive that these statistics/leaderboards are accurately displayed.
    \item \hyperref[req:SR19]{SR19}: Because the application will be released to the public within the capstone timeline, it is imperative that this version of the application takes into account the risk of photosensitive seizures.
    \item \hyperref[req:SR20]{SR20}: Effective education of octal arithmetic is an important goal of the application. To achieve this goal in the capstone timeline, the Tutorial / Hint Manager must show up to date hints / tutorial steps based on the game's state.
\end{itemize}

\subsection{Deferred Safety and Security Requirements}

\begin{itemize}
    \item \hyperref[req:SR3]{SR3}: Although creating a backup is important, due to the recreational nature of the application, it is not a significant detriment if data is lost or corrupted.
    \item \hyperref[req:SR4]{SR4}: Similar to SR3, because the data stored is not entirely important (other than it being secure), it is not our main priority to prevent data loss or corruption.
    \item \hyperref[req:SR10]{SR10}: Although general rules regarding how the leaderboards are modified will be set up during the capstone timeline, it is not immediately critical to stop malicious users from modifying competitive statistics / leaderboard results.
    \item \hyperref[req:SR11]{SR11}: This requirement is not possible without \hyperref[req:SR3]{SR3}, which itself is deferred. The reasoning for this requirement being deferred follows the same reasoning as \hyperref[req:SR3]{SR3}.
    \item \hyperref[req:SR21]{SR21}: Although addiction can be a concern, it cannot be prioritized over more prevelent risks such as photosensitive seizures. Additionally, addiction-prevention features like this already exist externally (e.g., screen time controls), so there are other methods in place to control usage if necessary while this requirement is deferred.
\end{itemize}

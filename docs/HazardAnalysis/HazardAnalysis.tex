\section{Introduction}

\subsection{Background}

A most perfect magic cube is a cube where each voxel's value is a distinct number from 1 to n\textasciicircum{}3 and all rows, columns, pillars, 2-dimensional diagonals, 3-dimensional diagonals (triagonals), and broken space diagonals in the cube sum to the same number, also called the magic constant. The order-eight cube is the smallest order most perfect magic cube. Using octal within this order-8 magic cube showcases the magic properties of the cube with the above prescribed lines summing to 4004, half lines summing to 2002, and the complementary numbers (+4 4 4 for the x y z coordinates from a given voxel) summing to 1001 (all in octal).

Our project, Magic 8, is a web-based application that serves as a recreational mathematics game as well as an educational tool for octal addition and subtraction. In this proposed game, players start with one voxel (number) in a most perfect magic cube visible while all other voxels remain hidden. The player must then complete tasks related to finding the voxels belonging to lines that sum to the magic constant. Each round of the game includes eight tasks that increase in difficulty as the player progresses.

\subsection{Hazard Definition}

A hazard is defined as a system state that if combined with a specific environmental condition, can cause harm/damage. Hazards can result from software defects or incorrectly defined system behavior. These hazards can be categorized as health, data, education, and usability hazards.


\section{Scope and Purpose of Hazard Analysis}

The purpose of this Hazard Analysis is to identify hazards related to the Magic 8 application and subsequently perform a Failure Mode and Effect Analysis (FMEA) to mitigate the found hazards. Below is the description of the losses that could be incurred because of the hazards.

\subsection{Health}

This category is described as the loss of health due to use of the system. This includes both physical health (e.g., photosensitive seizure) as well as mental health (e.g., bullying through the application).

\subsection{Data}

This category is described as the deletion, corruption, or leakage of data. One loss related to this category is the unauthorized disclosure of private user account information (e.g., password). Another loss is the corruption or deletion of data (both user data as well as game data).

\subsection{Education}

This category is described as the loss of educational value. This involves harming the user's knowledge of octal addition and subtraction by either teaching them incorrectly or adding to their confusion of the mathematical concept.

\subsection{Usability}

This category is described as the loss of user engagement, satisfaction, or trust. Any of these losses would reduce the usability of the application and subsequently make it a less valuable product.

\section{System Boundaries and Components}

The following subsections describe the main components of the system.

\subsection{User Database}

This component stores user account specific data including usernames, emails, passwords, and individual high scores.

\subsection{Competitive/Leaderboard Database}

This component stores data related to online, competitive statistics such as global high scores, fastest solve times, and rankings.

\subsection{Game State Manager}

This component handles the gameplay for the application. This involves taking in user actions and evaluating them against the current task, progressing through tasks in a round, etc.

\subsection{Visualization/Rendering Manager}

This component handles the rendering and projection calculations associated with the 3D visualization. This includes both the magic cube itself and highlighting related to the current task.

\subsection{Hint/Tutorial Manager}

This component handles the hints, feedback, and tutorial steps related to the game as well as educational help for octal arithmetic.

\subsection{User Interface}

This component handles user input and output for the labels, buttons, and text fields of the application. Essentially, this component handles all user input and output that is not related to rendering the 3D space.

\subsection{Task Generator}

This component handles the task generation process for a given round including generating both the problem and solution for a generated task and ramping up difficulty as a round progresses.

\section{Safety and Security Requirements}

\noindent\textbf{SR1\label{req:SR1}:} The system shall encrypt sensitive user data.

\noindent\textbf{SR2\label{req:SR2}:} The system shall store user account passwords as cryptographic hashes.

\noindent\textbf{SR3\label{req:SR3}:} The system shall automatically generate a backup for each database.

\noindent\textbf{SR4\label{req:SR4}:} The system shall log all transactions for each database.

\noindent\textbf{SR5\label{req:SR5}:} The system shall automatically save game progress every time there is a change in game state.

\noindent\textbf{SR6\label{req:SR6}:} The system shall attempt to save the game state three times before failing.

\noindent\textbf{SR7\label{req:SR7}:} The system shall ensure that a save state is valid before loading it as the current game state.

\noindent\textbf{SR8\label{req:SR8}:} The system shall ensure that each generated task has not already been generated in the current round.

\noindent\textbf{SR9\label{req:SR9}:} The system shall ensure that each generated task is solvable.

\noindent\textbf{SR10\label{req:SR10}:} The system shall only allow authorized users to modify competitive statistics and leaderboard records.

\noindent\textbf{SR11\label{req:SR11}:} The system shall restore database data from the most recent, valid backup in the event of database corruption or data loss.

\noindent\textbf{SR12\label{req:SR12}:} The system shall ensure that a generated solution correctly solves its related generated task.

\noindent\textbf{SR13\label{req:SR13}:} The system shall ensure that public usernames meet guidelines for user conduct.

\noindent\textbf{SR14\label{req:SR14}:} The system shall warn the user if their hardware specification does not meet minimum requirements to run the application.

\noindent\textbf{SR15\label{req:SR15}:} The system shall ensure that the current highlighting is consistent with the game state.

\noindent\textbf{SR16\label{req:SR16}:} The system shall allow users to confirm parsed data before submitting.

\noindent\textbf{SR17\label{req:SR17}:} The system shall inform the user if an input event is not recognized.

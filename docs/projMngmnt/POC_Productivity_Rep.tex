\section{Demo Plans}

% \wss{What is your feasibility risk?}

% \wss{What will you be demonstrating}

The feasibility risks associated with this project lie in three areas:

\begin{itemize}
  \item \textbf{3D visualization (primary risk).} The team has limited experience
  with 3D graphics, and we plan to implement the projection calculations ourselves
  rather than rely on a pre-built renderer. It is therefore uncertain whether we
  can correctly project the magic cube onto the screen and keep that projection
  accurate and readable as the viewpoint changes (e.g., rotation and zoom
  requested through the user interface). Because the cube is $8\times8\times8$,
  the user must also be able to isolate a single layer and see which layer and
  cells are selected in order to reach and choose cells inside the cube.
  \item \textbf{Basic gameplay (primary risk).} The eight tasks are the core of the
  project. If the game logic cannot correctly present each task and evaluate the
  user's answers, the project cannot move forward.
  \item \textbf{WebAssembly conversion (secondary risk).} We intend to convert our
  Python application to WebAssembly using pygbag. Established tools exist for
  this, so the risk is smaller, but we still need to confirm that our application
  (including the 3D projection) works correctly once converted.
\end{itemize}

Our demonstration will consist of a minimal version of the game in which a single
fixed round of the eight prescribed tasks can be completed from start to finish.
The tasks will be hardcoded, so the numbers presented to the user are always the
same. This lets us exercise/demonstrate the game logic without implementing randomized round
generation. The demonstration addresses both primary risks: the user will
navigate the 3D cube by rotating and zooming, select a single layer along any
axis (with the other layers faded or hidden), step between layers and restore
the full cube, and complete each task, with the chosen layer and selected cells
highlighted. To address the secondary risk, the
demonstration will run in a web browser as a WebAssembly build served from a
local test server.

The demonstration will be considered successful if the cube is projected
correctly and updates as the user changes the view through the interface, if
the user can isolate and step through layers with the chosen layer and selected
cells clearly highlighted, if all
eight tasks can be completed without errors in the underlying game logic, and if
all of the above runs as a WebAssembly build in the browser.

If the 3D visualization proves infeasible, the team will evaluate moving to a
static or 2D representation of the cube. If the core gameplay proves infeasible,
a significant reassessment of the project scope would be required. If the
WebAssembly conversion proves unreliable, the team will evaluate alternative
conversion tools or moving the frontend to JavaScript.

Lower-risk features are intentionally left out of the demonstration, including
randomized round generation, scoring, tutorials, hints, settings, game saving, navigation between screens and menus, user accounts, deploying
the application online, and competitive features (daily challenges,
leaderboards).

\section{CICD via GitHub Actions}

%\wss{Say how CICD technology is used and will be used in your project.}

%\wss{Provide links to your CICD yaml files}

The Magic-8 project uses GitHub Actions to implement CI/CD. GitHub Actions automates parts of the development workflow by executing predefined tasks when changes are pushed to the repository or when pull requests are created or updated.

Currently, GitHub Actions is used to automate the compilation of project documentation. These workflows compile the corresponding LaTeX files and generate PDF documents, allowing compilation errors to be identified early and ensuring that documentation can be built consistently across development environments. It also automates the deployment of the generated documentation to GitHub Pages.

As development of Magic-8 continues, CI/CD workflows will be expanded to include automated software testing and validation. This will allow changes to be checked for potential errors before they are merged into the main development branch.

The GitHub Actions workflow configuration files are stored in the repository's \texttt{.github/workflows/} directory. The following workflows are currently used or planned:

\begin{itemize}
\item \textbf{Documentation Build:} Automatically compiles LaTeX documentation into PDF files and identifies compilation errors.
\item \textbf{Automated Testing (Planned):} Executes automated tests to verify application functionality whenever changes are pushed or submitted through a pull request.
\end{itemize}

The GitHub Actions configuration files can be found below:

\begin{itemize}
\item \href{https://github.com/Jacob-MB/magic-8/blob/main/.github/workflows/latex-pages.yml}{Documentation Build Workflow}
\end{itemize}

\subsection{Charter and Trigger Summary}

The Team charter lays out the following expectations:

\begin{itemize}
\item All members in attendance in person for meetings with the supervisor unless an acceptable excuse as listed in the following section is provided
\item Members with information or roles relevant to the meeting agenda should be present for the team’s personal meetings with online or in-person attendance
\item Members are expected to stay till the end of meetings they attend unless significant external circumstances require them leave early. 
\item Members are expected to arrive within 5 minutes of the agreed meeting start time for both personal and supervisor meetings. 
\end{itemize}

An acceptable excuse is one that falls within the following categories:

\begin{itemize}
\item Academic (classes, tutorials, labs)
\item Medical (Major sickness, hospital visit, etc.)
\end{itemize}

In the case of an emergency members are expected to:

\begin{itemize}
\item Let all team members know as soon as possible if you have to miss a meeting and follow-up later to catch up on assigned work / missed discussions 
\item If missing a deadline, let team know as soon as possible and email instructor to explain situation.
\end{itemize}

In addition to these members are expected to maintain the following attitdes and practices:

\begin{itemize}
\item Team members should be respectful of one another.
\item All team members should have a positive attitude and be open to other peoples’ ideas. 
\item Work brought to the team should be in a complete enough state to receive meaningful feedback from another team member.
\item Team members are expected to arrive to meeting having reviewed relevant issues, pull requests, and documents assigned to them beforehand 
\end{itemize}

A violation of any of the previously listed point in this section count trigger a reference of the resolution plan.
